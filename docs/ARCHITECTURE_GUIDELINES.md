# Архитектурные и кодовые требования

## Основные принципы

- Не добавляйте функции в список зависимостей `useEffect`; выносите их за пределы эффекта или оборачивайте в `useCallback`, чтобы зависимости оставались стабильными и предсказуемыми.
- Если файл превышает 300 строк, выделите отдельные компоненты или функции и вынесите их в самодостаточные модули; поддерживайте небольшие, фокусированные файлы.
- Стремитесь к переиспользуемым блокам: проектируйте компоненты и утилиты так, чтобы их можно было подключать в разных частях приложения без дублирования логики.

## React и Hooks

- Отдавайте предпочтение Server Components, когда нет необходимости в клиентском состоянии или эффектах; подключайте `"use client"` только там, где требуется интерактивность.
- Держите состояние максимально локальным и минимизируйте количество `useState`; для кэширования данных используйте React Query или серверные загрузчики Next.js.
- Избегайте derived state внутри `useEffect`; вычисляйте значения на основе пропсов прямо в рендере или через мемоизации (`useMemo`, `useCallback`).
- Следите за чистотой эффектов: каждый `useEffect` должен возвращать функцию очистки при подписках, таймерах и побочных эффектах.
- Не мутируйте пропсы и состояние; используйте иммутабельные обновления и утилиты для работы с массивами/объектами.

## Структура компонентов

- Соблюдайте композицию: простые компоненты размещайте в `components/common`, а доменные — в подпапках (`components/feed`, `components/llm`).
- Прописывайте интерфейсы пропсов в начале файла и экспортируйте компоненты в PascalCase; вспомогательные функции держите ниже основного компонента либо переносите в `lib/`.
- Разделяйте разметку, состояние и побочные эффекты; выносите сложную бизнес-логику в хуки (`useSomething`) внутри `app/` или `lib/`.

## TypeScript

- Используйте `type` вместо `interface`, когда нужна композиция через пересечение; для публичных контрактов компонентов допускаются `interface`.
- Включайте строгие флаги (`strict`, `noImplicitAny`); не отключайте проверки на уровне строк, лучше уточняйте типы.
- Типизируйте асинхронные функции через `Promise<ReturnType>` и описывайте модели данных в отдельных файлах внутри `lib/`.
- Предпочитайте `enum`-ам объединения литералов (`type Status = "draft" | "published"`), чтобы избежать избыточного JS-кода.

## Next.js

- Соблюдайте соглашения App Router: файлы `page.tsx`, `layout.tsx`, `loading.tsx` и `error.tsx` размещайте в соответствующих сегментах.
- Для запросов на сервере используйте серверные действия или API-роуты; клиентские компоненты не должны хранить секретные ключи и конфигурацию.
- Настраивайте метаданные через экспорт `metadata`; изображения обслуживайте через `next/image` для оптимизации.
- Поддерживайте маршруты и общий стиль, описанные в `docs/start.md`, чтобы дизайн оставался консистентным.

## JavaScript и качество кода

- Избегайте неявных преобразований; используйте строгие сравнения и явные парсеры (`Number()`, `Boolean()`).
- Логика должна быть покрыта защитой от ошибок: проверяйте входящие данные, обрабатывайте пустые состояния и ошибки сетевых запросов.
- Сохраняйте чистоту импорта: группируйте системные, внешние и локальные импорты, удаляйте неиспользуемые зависимости.
- Добавляйте JSDoc-комментарии там, где поведение не очевидно, и обновляйте их при изменениях API.

## Тестирование и проверка

- При появлении тестового стека располагайте файлы рядом с исходниками (`Component.test.tsx`) и покрывайте критические ветки, включая ошибки.
- Перед отправкой PR выполняйте `bun run lint`, `bun run build` и ручную проверку UI на ключевых разрешениях.
- Фиксируйте найденные баги и технические долги в issue-трекере, а в PR описывайте сценарии проверки.
